# Chrome API Mock 插件设计方案

> 状态：已确认的设计基线  
> 更新时间：2026-09-08  
> 适用范围：第一阶段 MVP 及后续演进。后续实现、讨论和需求变更均以本文档为准。

## 1. 目标与范围

本插件用于前端开发完成、后端接口尚未可联调时，在浏览器中为页面接口提供本地 Mock 响应。首期仅面向 Chrome，规则和模型配置均保存在本机，不建设服务端或团队同步能力。

核心目标：

- 拦截页面的 `fetch` 与 `XMLHttpRequest` 请求，并按本地规则返回 Mock 结果。
- 支持改写状态码、响应体、请求 Header、响应 Header 和响应延迟。
- 支持规则命名、文件夹管理、规则/文件夹开关、重复规则提示及命中日志。
- 可选开启当前标签页的全部 HTTP 流量监听，用于观察请求和快速创建规则。
- 用户配置自己的大模型服务，用接口文档生成规则，并通过对话修改规则。
- 提供网页悬浮面板、Chrome 侧边栏和独立工作台 Tab 三种操作入口。

## 2. 产品边界与技术约束

### 2.1 浏览器与请求范围

- 首期仅支持 Chrome，采用 Manifest V3。
- 默认 Mock 覆盖页面主环境发出的 `fetch` 与 `XMLHttpRequest`，包括 Axios、jQuery AJAX 等常见使用方式。
- 默认模式不依赖 Chrome 调试协议，因此不会出现“正在调试此页面”的浏览器提示。
- 页面导航、图片/CSS/JS 子资源、WebSocket、浏览器扩展页、`chrome://` 页面等不属于默认 Mock 拦截范围。

### 2.2 全量 HTTP 监听开关

开启“监听全部 HTTP 请求”后，插件通过 Chrome DevTools Protocol 的 Network 域监听当前 Tab 的网络事件。

- 可展示文档、fetch/XHR、脚本、样式、图片等资源的 URL、方法、状态码、Header、耗时和资源类型。
- 默认只采集元信息；“抓取响应体”为可选深度能力，防止大型资源影响性能。
- 支持从某条流量记录中一键生成 Mock 规则。
- Chrome 会显示该页面正在被插件调试；该模式可能与 DevTools 或其他调试工具的调试连接冲突。
- 首期该模式以“观察、筛选和生成规则”为主；响应改写以默认的 fetch/XHR Mock 能力为主。

### 2.3 窗口形态

纯 Chrome 插件不能创建任意位置、始终置顶的原生桌面窗口，也不能完全替代 DevTools 的停靠机制。因此采用官方可实现的三种形态：

- 网页内悬浮面板：注入网页内容区域，适合快速操作。
- Chrome Side Panel：固定在浏览器右侧，是最接近 F12 工作方式的形态。
- 独立工作台 Tab：完整的规则管理、流量分析、AI 工作区。

悬浮面板工具栏中的“固定”按钮用于打开 Side Panel；另提供“在新标签页打开工作台”。

## 3. 用户界面与导航

### 3.1 完整工作台

| Tab | 核心能力 |
| --- | --- |
| 流量监听 | 默认首个 Tab；当前 Tab 网络流量、筛选、请求详情、命中结果、一键创建规则 |
| Mock 规则 | 文件夹树、规则列表、搜索、启停、新增/编辑、导入导出、冲突提示 |
| AI 助手 | 文档导入、规则生成、对话修改、`@` 引用、变更预览 |
| 设置 | 模型配置、权限和监听状态、悬浮面板偏好、数据维护 |

规则页采用左右两栏：左侧为可收起的文件夹、规则文件操作与接口列表侧栏，右侧为选中接口的独立二级编辑面板。再次点击已选接口可收起右侧面板。字段变更自动防抖保存；JSON 未完成或无效时暂停保存并提示。删除操作位于规则卡片右侧。

### 3.2 网页悬浮面板

悬浮面板使用 Shadow DOM 隔离网页样式，最小尺寸为 640 × 480，可拖动、八方向缩放并记忆布局；允许水平部分移出视口，但始终保留至少 48px 以便拖回。切换到 Chat 时自动展开。

| Tab | 用途 |
| --- | --- |
| Mock | 当前页面相关规则的快捷开关、命中数量、快速新建规则 |
| 流量 | 当前 Tab 最近的 fetch/XHR 请求、规则命中状态及快捷查看 |
| Chat | 与配置的大模型对话，通过 `@` 引用接口规则或文件夹 |

悬浮面板、Side Panel 和完整工作台共享规则、模型配置和对话会话。复杂编辑可从任一入口跳转到完整工作台。

## 4. 规则与文件夹模型

### 4.1 文件夹

- 文件夹支持层级、命名、排序和启停。
- 每条规则归属一个文件夹。
- 规则实际生效的前提是：规则已启用，且其所在文件夹及所有父级文件夹均已启用。
- 关闭文件夹只使其下规则不生效，不删除规则数据。

### 4.2 规则数据结构

```ts
type MockRule = {
  id: string
  name: string
  folderId: string
  enabled: boolean
  priority: number

  match: {
    url: string
    urlMode: 'exact' | 'prefix' | 'wildcard' | 'regex'
    methods: string[]
    query?: Record<string, string>
    requestHeaders?: Record<string, string>
    requestBodyMatcher?: string
  }

  requestRewrite?: {
    enabled?: boolean
    headers?: Record<string, string>
  }

  response: {
    status: number
    headersEnabled?: boolean
    headers: Record<string, string>
    bodyType: 'json' | 'text' | 'empty'
    body: unknown
    delayMs: number
  }

  metadata: {
    createdAt: number
    updatedAt: number
    source: 'manual' | 'ai' | 'import' | 'traffic'
  }
}
```

请求 Header 改写只有在其启用复选框勾选、且真实请求继续发送时才生效；未启用时保留页面原始请求 Header。响应 Header 改写只有在其启用复选框勾选时才生效；未启用时，Mock 响应仅自动补充必要的 `Content-Type`。

### 4.3 规则匹配与选择

规则匹配依次检查：启用状态、文件夹状态、HTTP 方法、URL、Query、请求 Header、请求体条件。

当存在多条可命中规则时，按以下顺序选择最终规则：

1. URL 匹配精确度：精确 > 前缀 > 通配 > 正则；
2. 用户配置的 `priority`：数值越高优先；
3. 最近修改的规则优先。

每次命中日志必须记录候选规则、最终规则及选择原因，便于排查。

## 5. 重复与冲突规则检测

插件不只检查 URL 字符串是否相同，还需分析规则的可匹配请求范围。

| 类型 | 判断条件 | 界面表现 |
| --- | --- | --- |
| 明确重复 | HTTP 方法有交集，且 URL 匹配条件等价，其他已配置条件也等价或更宽松 | 红色高亮与“明确重复”提示 |
| 可能冲突 | HTTP 方法有交集，且精确/前缀/通配/正则的 URL 匹配范围可能重叠 | 黄色高亮与“可能冲突”提示 |
| 不冲突 | 方法无交集，或可确定 URL 匹配范围无交集 | 不提示 |
| 当前不生效 | 规则或任意上级文件夹已关闭 | 保留冲突提示，同时标记为“当前不生效” |

检测时应同时考虑方法、URL 模式、Query、Header、请求体等条件，避免把 `GET /users` 与 `POST /users` 错误标为重复。对无法严格判定的正则表达式，以“可能冲突”呈现，而不阻止保存。

规则列表、编辑页和保存前均展示冲突信息，并提供：查看冲突规则、跳转编辑、调整优先级、禁用规则和继续保存。

## 6. AI 与文档解析

### 6.1 模型配置

用户自行配置：

- 模型服务 Base URL；
- API Key；
- 模型名称；
- OpenAI 兼容 API 格式；
- 可选自定义请求 Header。

插件只负责从浏览器直接调用用户配置的模型服务，不提供后端中转。规则、文档和对话内容会直接发送至该模型服务，界面需明确提示此数据流向。

模型配置仅本地保存。API Key 使用扩展本地存储，不同步至服务器；产品不应承诺其具备操作系统级密钥库的安全等级。

### 6.2 文档输入和规则生成

- OpenAPI / Swagger URL、JSON、YAML：优先进行确定性本地解析。
- 普通 URL：通过用户授权的站点权限获取内容，再提取接口定义。
- 本地文件：支持 JSON、YAML、Markdown；PDF 作为后续增强能力。
- 模型生成的结果必须是受 Schema 约束的结构化规则草稿。

生成流程：

```text
接口文档 → API Schema → AI 规则草稿 → 本地 Schema 校验与冲突检测 → 用户预览确认 → 保存
```

AI 不可直接绕过预览写入规则库。

### 6.3 Chat 与 `@` 智能引用

在完整工作台和悬浮面板 Chat 中，用户输入 `@` 时立即显示候选菜单：

- 按规则名称、接口自定义名称、URL、文件夹路径进行模糊过滤；
- 分组展示“接口规则”和“文件夹”；
- 支持鼠标、上下键、Enter 选择，Esc 关闭；
- 选择后插入可识别的引用标签；
- 发送模型前，将标签解析为对应规则或文件夹的结构化上下文，而不是只发送名称文本。

示例：

```text
把 @用户管理 / @用户列表接口 的返回列表改为 20 条，且头像使用随机图片
```

模型应返回新建、修改或删除规则的差异草稿；用户审阅后才能应用。

## 7. 本地存储与权限

| 数据 | 存储位置 | 说明 |
| --- | --- | --- |
| 文件夹、规则、命中日志、对话记录 | IndexedDB | 适合结构化数据和较大容量 |
| 模型配置、界面偏好、开关状态 | `chrome.storage.local` | 不进行云同步 |
| 页面注入与 Mock 状态 | 当前 Tab 会话状态 | 关闭 Tab 后自动清理 |

按需申请权限，避免初次安装时索要全部站点访问权：

- 用户对指定站点开启 Mock 时请求该站点的 Host Permission；
- 用户开启全量 HTTP 监听时请求 `debugger` 权限并展示影响说明；
- 用户读取在线 API 文档或调用自定义模型地址时，按需请求对应域名权限。

## 8. 扩展架构

```text
React 工作台 / Side Panel / 悬浮面板
                ↕
      MV3 Background Service Worker
       ↙            ↓             ↘
IndexedDB      规则匹配服务      Chrome Debugger Network 监听
                                      ↑
页面 Main World 注入脚本（fetch/XHR 代理）
```

- **Main World 注入脚本**：代理 `fetch` 和 `XMLHttpRequest`，与 Content Script 通过带随机标识的消息桥通信。
- **Content Script**：渲染 Shadow DOM 悬浮面板，负责页面级交互与消息转发。
- **Background Service Worker**：保存和查询规则、协调 Tab 状态、处理按需权限、调用 CDP 监听。
- **React 页面**：工作台与 Side Panel 共享组件和状态模型。
- **本地校验层**：负责规则 Schema 校验、冲突检测、AI 草稿校验及导入文件校验。

远程模型返回内容不得作为远程可执行代码加载；模板、正则与动态数据能力均需在受限 Schema 内表达。

## 9. 实施阶段

### 第一阶段：可用 MVP

1. Chrome MV3 基础工程；
2. 完整工作台、网页悬浮面板、Chrome Side Panel；
3. 文件夹与规则本地 CRUD、启停、导入导出；
4. fetch/XHR 请求匹配与 Mock 响应；
5. 状态码、响应体、请求/响应 Header、延迟配置；
6. 命中日志与命中解释；
7. 重复/冲突规则检测与高亮；
8. 悬浮面板 Mock / 流量 / Chat 三 Tab；
9. 自定义模型基础配置与 Chat `@` 智能引用。

### 第二阶段：流量与文档

1. 全量 HTTP 监听开关与流量详情；
2. 从流量记录创建规则；第一阶段的 fetch/XHR 流量也可直接创建并自动填充 URL、方法与可用状态码；
3. OpenAPI / Swagger 本地解析；
4. 基于接口文档生成规则草稿及确认流程。

### 第三阶段：AI 增强

1. 普通文档 URL 与本地文档的 AI 解析；
2. AI 对话生成规则差异与批量应用；
3. 动态 Mock 数据模板，例如随机用户、时间、分页数据；
4. 性能优化、错误诊断与体验完善。

## 10. MVP 验收标准

- 用户能新建文件夹和规则，开关文件夹后其所有子规则均停止命中。
- 页面 `fetch` 与 XHR 请求能按 URL 和方法命中 Mock，并返回配置的状态码、Header、数据和延迟。
- 对同一接口的明显重复规则和可能重叠规则，系统能在列表、编辑页及保存前给出可操作提示。
- 悬浮面板能在 Mock、流量、Chat 三个 Tab 间切换，并可打开 Side Panel 或完整工作台。
- Chat 输入 `@` 时能检索并选择规则或文件夹，发送时能得到正确的结构化引用上下文。
- 用户能配置兼容 OpenAI API 的模型服务；模型造成的规则变更必须先预览、校验，再确认保存。
- 启用全量 HTTP 监听后，用户能查看当前 Tab 的网络请求并从其中创建 Mock 规则。
